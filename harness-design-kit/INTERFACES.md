# 인터페이스 계약
상태: 초안. 아래는 언어와 통신 방식에 독립적인 설계 틀이다. 학생의 D02~D07 선택 후 구체적 타입, 예시와 오류를 채운다. API는 프로그램 사이의 약속이며 HTTP만 뜻하지 않는다.

## 제품의 작업 계약
| 동작 | 입력에서 정할 것 | 출력에서 정할 것 | 오류·경계 |
|---|---|---|---|
| 작업 시작 | 요청, 세션 선택, 작업 폴더 식별 | 작업 식별자와 최초 상태 | 빈 요청, 없는 세션, 실행 중 중복 요청 |
| 상태 조회 | 작업 식별자 | 상태, 진행 내역, 결과 또는 오류 | 없는 작업, 다른 세션의 작업 |
| 변경 승인/거절 | 작업·승인 식별자, 표시한 변경에 대한 선택 | 결정 반영 결과 | 중복/만료 승인, 승인 후 변경 내용 바뀜 |
| 결과 조회 | 작업 식별자 | 결과, 근거, 변경·테스트 기록 | 미완료를 완료로 보여 주지 않음 |
| 세션 이어가기 | 세션 식별자, 새 요청 | 연결된 새 작업 | 재시작 후 기록이 없으면 복원했다고 말하지 않음 |

작업 상태: queued → running → (waiting_approval → running)? → completed/failed. D09에서 취소·동시실행을 후속으로 미뤘으므로 cancelled는 이번 범위에서 제외(CHOSEN, 2026-09-08). 거절 이후는 실패로 종료하지 않는다 — 채팅창에 "적용하지 않았습니다"를 표시하고 completed(변경 없음)로 마무리하며, 재계획은 사용자가 다음 메시지로 새 작업을 시작하는 것으로 처리한다(대화형 UI라 별도 재계획 상태를 두지 않음, CHOSEN).
승인은 특정 작업의 특정 도구 입력/변경 내용에 연결한다. 사용자가 본 내용이 바뀌면 그 승인을 재사용하지 않는다.

### 구체적 계약 한 개
- 이름: 작은 텍스트 파일 읽기와 질문 답변
- 입력 타입과 허용 범위: 사용자가 첨부한 작업 폴더 안의 `.txt` 또는 `.md` 파일 1개와 자연어 질문 1개. 파일 크기는 첫 구현에서 1 MiB 이하로 제한한다.
- 정상 입력 예: `메모.txt`에 `회의 시작: 오후 3시`가 있고, 사용자가 `회의 시작 시간이 언제야?`라고 질문
- 정상 출력 예: 모델이 파일 내용을 근거로 `오후 3시입니다.`라고 답하고, 채팅창에 읽기·답변 완료 상태를 표시
- 잘못된 입력과 오류 출력 예: 지원하지 않는 확장자·없는 파일·1 MiB 초과 파일은 파일 읽기 실패로 표시하고 모델을 호출하지 않음. 모델 연결·응답 파싱 실패는 답변 실패로 표시하고 성공 답변으로 기록하지 않음.
- 상태 변화/부작용: `queued → running → completed/failed`. 파일 원문과 대화 원문은 별도 저장하지 않으며, 파일은 읽기만 하고 변경하지 않는다.
- 재시도·중복 요청 정책: 같은 첨부와 질문은 사용자가 다시 제출하면 새 작업으로 처리한다. 첫 구현에서는 자동 재시도하지 않는다.
나머지 동작에도 같은 틀을 적용한다. API의 모든 필드를 모델의 자연어 판단에 맡기지 않는다.

## UI와 통신 매핑
CLI를 선택하면 명령/옵션과 내부 함수 호출을 위 계약에 대응한다. 로컬 웹을 선택하면 HTTP 메서드·경로·본문·응답 코드와 인증 범위를 정한다. CLI 구현에 웹 서버를 의무적으로 추가하지 않는다.
- 선택한 방식: D02에 따라 별도 CLI/웹 없이 기존 `chat_assistant.py` 채팅창을 그대로 쓴다(CHOSEN). 사용자의 자연어 메시지 자체가 "작업 시작" 요청이고, HTTP 경로나 별도 명령어를 새로 만들지 않는다.
- 명령 또는 HTTP 경로와 계약의 대응: 없음(내부 함수 호출로 대응). "작업 시작"=사용자 메시지 제출, "상태 조회"=채팅창의 진행 메시지 자체(별도 폴링 API 없음, 같은 스레드에서 동기 실행), "변경 승인/거절"=팝업의 승인/거절 버튼 또는 다음 채팅 메시지("승인"/"거절"), "결과 조회"=채팅창에 표시된 최종 답변.
- 진행 결과를 보여 줄 방식: `self._log()`로 채팅창에 역할별 말풍선(assistant/success/error)으로 단계 표시(예: "한글 읽는 중...", "엑셀 비교 중..."). 별도 진행률 바는 두지 않는다.

## 모델 제공자 연결부
제품 내부에서는 모델에게 전달할 대화/도구 정보와 돌려받을 최종 답/도구 요청을 정한다. provider adapter는 각 제공자의 요청·응답을 이 내부 계약으로 변환한다.
- 첫 제공자/모델: Ollama `qwen3.5:2b`를 먼저 호출하고, 연결·응답 실패 시 OpenAI 호환 Colab vLLM `cyankiwi/Qwen3.5-4B-AWQ-4bit`로 재시도한다.
- 사용 API와 공식 문서: Ollama `/api/chat`(tools 파라미터, [Ollama tool calling](https://ollama.com/blog/tool-support)) 우선 호출. 실패 시 OpenAI 호환 vLLM `/v1/chat/completions`로 폴백.
- 도구 호출·결과 연결에 필요한 식별자 처리: 모델이 반환한 `tool_call.id`를 그대로 보존해 실행 결과(ToolResult)와 짝짓는다. provider가 id를 안 주면(Ollama 일부 응답에서 관찰됨) 그 응답 안에서의 등장 순번으로 내부 id(`call_0`, `call_1`...)를 붙이고, 이 id는 "실제 provider가 발급했다"고 기록하지 않는다(harness_lab.OllamaProvider와 같은 처리).
- 일반 답과 도구 호출, 여러 도구 요청의 처리 순서: 응답에 `tool_calls`가 있으면(1개 이상) 등장 순서대로 하나씩 검사→실행하고, 각 결과를 대화에 도구 메시지로 추가한 뒤 다시 모델을 호출한다(반복). `tool_calls`가 없고 텍스트만 있으면 그 텍스트를 최종 답으로 보고 반복을 끝낸다.
- 지원하지 않는 기능, 파싱 실패, 네트워크 오류: Ollama 실패 원인을 보존한 채 vLLM fallback을 한 번 시도한다. 두 provider가 모두 실패하거나 응답 본문이 비어 있으면 작업을 `failed`로 표시하고 성공 답변을 반환하지 않는다.
- 제한 횟수/시간과 재시도 대상: 모델 호출 최대 8회, 도구 실행 1건당 최대 30초, 작업 전체 최대 120초(HWP COM 자동화가 harness_lab 기본값보다 느릴 수 있어 낮게 시작 — 실측 후 IMPLEMENTATION_PLAN.md에 조정 기록). 한도 도달 시 completed가 아니라 failed로 표시하고 "반복 한도 도달"과 그때까지 실행된 도구 목록을 사용자에게 보여준다. 자동 재시도 대상은 provider 연결 실패(→vLLM 폴백)뿐이며, 도구 실행 오류는 재시도하지 않고 모델에게 오류로 반환해 모델이 스스로 판단하게 한다.
OpenAI와 Ollama에 같은 필드를 보내면 언제나 같은 기능이 동작한다고 가정하지 않는다. 모델 응답은 실행 전에 구조와 인자를 검사한다.

## 실행 도구 계약
| 도구 | 인자/반환 예 | 허용 범위 | 승인·오류 |
|---|---|---|---|
| 읽기 도구 `read_small_text_file` | 입력 `{"path": "notes.txt"}` → `{"ok": true, "file_name": "notes.txt", "text": "..."}` | 사용자가 첨부한 `.txt`/`.md` 1개, 1 MiB 이하 | `{"ok": false, "error": {"code": "UNSUPPORTED_EXTENSION\|FILE_NOT_FOUND\|FILE_TOO_LARGE", "message": "..."}}`. 승인 불필요(읽기 전용) |
| 수치검증 도구 `verify_numbers` | 입력 `{}`(현재 첨부된 한글+엑셀을 그대로 씀) → `{"ok": true, "match": n, "mismatch": n, "unverifiable": n, "ambiguous": n}` | 지금 열려있는 한글 문서 + 첨부된 엑셀 1개 이상 | `{"ok": false, "error": {"code": "NO_SOURCE_ATTACHED\|NO_DOCUMENT_OPEN", ...}}`. D06에 따라 승인 없이 즉시 색상 적용(자동저장 없음) |
| 코드 결함 조회 도구 `read_fixture_code` | 입력 `{}` → `{"ok": true, "code": "...", "test_result": "FAIL", "test_output": "..."}` | `coding_fixture/` 폴더 고정 파일 2개(함수+테스트)만 | `{"ok": false, "error": {"code": "FIXTURE_NOT_FOUND"}}` |
| 코드 변경 제안 도구 `propose_code_fix` | 입력 `{"new_code": "def ...:\n ..."}` → `{"ok": true, "diff": "...", "approval_id": "call_N"}`(파일엔 아직 미적용, 채팅창에 변경 전/후 표시) | `coding_fixture/`의 지정 함수 파일 1개만 | `{"ok": false, "error": {"code": "SYNTAX_ERROR\|EMPTY_CHANGE"}}`. 이 도구 자체는 파일을 바꾸지 않음(제안만) |
| 변경 적용+테스트 함수 `apply_fix_and_test`(모델 도구 아님) | 입력 `{"approval_id": "call_N", "approved": true\|false}` → 승인시 `{"ok": true, "applied": true, "test_result": "PASS\|FAIL", "test_output": "..."}`, 거절시 `{"ok": true, "applied": false}`(파일 불변) | 같은 세션에서 방금 제안된 `approval_id`만(다른 id·재사용은 캐시된 이전 결과 반환 - 멱등성) | `{"ok": false, "error": {"code": "UNKNOWN_APPROVAL_ID\|TEST_TIMEOUT"}}`. 지정된 pytest 파일 외 임의 명령 실행 불가, 테스트 시간 제한 10초. **모델이 스스로 `approved: true`를 골라 호출하면 R05(승인 없는 변경 금지)가 무력화되므로, 이 함수는 도구 스키마에 넣어 모델에게 노출하지 않는다** — 채팅창이 사용자의 실제 "승인"/"거절" 메시지를 결정론적으로 감지했을 때만(기존 parse_ignore_index와 같은 패턴) 직접 호출한다. |
| (기존 6개 HWP 도구: polish_to_formal_style/insert_table/insert_numbering/merge_weekly_reports/fit_to_one_page) | D05 첫 범위 밖 — 기존 구현 유지, 이번 재설계에서 파라미터 스키마만 명시(각 함수 docstring 참고) | 기존과 동일 | 기존과 동일 |
실행 도구 내부의 파일·명령 검사는 모델의 지시와 무관하게 코드 레벨에서 적용한다. 임의 셸 명령을 허용하는 것은 별도의 권한 확대이며 이번 범위에 포함하지 않는다. `apply_fix_and_test`의 `approval_id`는 `propose_code_fix` 호출 1회당 새로 발급하고, 같은 id로 두 번째 적용 요청이 오면(중복 승인) 재실행하지 않고 이전 결과를 그대로 반환한다(멱등성).

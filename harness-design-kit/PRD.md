# 개인 에이전트 하네스 PRD
상태: 설계 대화 전. OPEN을 AI가 임의로 채우지 않는다.

## 제공된 제품 목표
사용자가 자연어로 작업을 요청하면 모델이 필요한 도구를 선택하고, 내 프로그램이 이를 검사·실행하여 결과를 다시 모델에 전달한다. 자료를 읽는 범용 작업과 코드를 수정하고 검증하는 코딩 작업을 모두 다룬다. 사용자는 진행 상황과 실패 이유를 확인할 수 있다.
PRD(Product Requirements Document)는 무엇을 누구를 위해 만들고 어떤 결과를 완료로 볼지 기록한다. 구현 방법의 모든 세부사항을 미리 고정하는 문서는 아니다.

## 학생이 완성할 사용자 이야기
D01 사용자/업무: CHOSEN
- 나는 사용자로서 한글 문서에 기재된 수치를 엑셀 파일의 값과 대조해 검증하고 싶다.
- 지금 불편한 점: 문서의 문맥을 읽어 수치를 확인하지 않고 엑셀에 나온 숫자만 가지고 검증한다.
- 실제로 성공했다고 판단할 결과: 문맥을 이해해 비교한 수치를 일치=파랑, 불일치=빨강, 한글 문서나 엑셀 파일 한쪽에만 존재=초록으로 표시한다. 문맥 연결이 불명확한 수치는 회색으로 표시하고 “확인 필요”로 기록한다.
- 실습용 자료: 한글 문서와 엑셀 파일

## 학생의 선택
D02 플랫폼: CHOSEN — 별도 프로그램을 새로 만들지 않고 기존 프로그램 안에 `문서 수치 검증` 전용 화면 또는 메뉴를 추가한다. 기존 프로그램의 실행 환경과 도구 실행 컴퓨터를 유지한다.
D03 언어: CHOSEN — Python. 기존 프로그램이 Python으로 구성되어 있어 현재 기능과 모듈을 재사용한다.
D04 첫 provider: CHOSEN — Ollama의 로컬 모델 `qwen3.5:2b`. 기존 프로그램의 로컬 실행과 개인정보 보호 방침을 유지하며, 실제 도구 호출 지원 범위는 구현 시 확인한다.
D05 첫 작업과 도구 범위: CHOSEN — 한글 문서 1개와 엑셀 파일 1개 이상을 읽어 문맥 기반 수치를 비교하고, 결과를 한글 문서에 색상으로 표시한다. 숫자 값이 같다는 사실만으로 일치로 판정하지 않고, 항목명·주변 문장·단위 등 문맥상 같은 항목으로 연결된 경우에만 비교한다. 같은 숫자가 여러 번 등장할 때 문맥 연결이 불명확하면 회색으로 표시하고 “확인 필요”로 기록한다. 모든 연도 문맥에서 4자리 연도와 앞에 작은따옴표를 붙인 2자리 연도는 같은 연도로 정규화한다(예: `2026`과 `'26`). 목차나 항목기호인 `1.`, `1)`, `(1)` 등의 숫자는 검증 대상에서 제외한다. 자동 저장하지 않으며 PDF·임의 폴더 탐색·임의 셸 실행은 초기 범위에서 제외한다.
**최소 코딩 시나리오(2026-09-08 추가, R04/R08 근거 확보)**: 지정한 실습 폴더(`coding_fixture/`) 안의 작은 결함 함수 1개 + 그 함수를 검사하는 pytest 테스트 1개로 범위를 제한한다. 사용자가 “고쳐줘”라고 요청하면 모델이 결함을 찾아 변경안을 제안하고, 채팅창에 변경 전/후를 보여준 뒤 사용자가 승인해야만 실제 파일에 적용한다. 거절하면 파일은 그대로 두고 그 사실을 알린다. 적용 후에는 지정된 테스트만 자동 실행해 통과 여부를 보고한다. `coding_fixture/` 폴더 밖 경로나 지정된 테스트 외 임의 명령 실행은 거부한다.
D06 승인 방식: CHOSEN — 별도 결과표 승인 없이 사용자가 검증을 실행하면 현재 열린 한글 문서의 수치에 즉시 색상을 적용한다. 파일 자동 저장은 하지 않는다.
D07 세션과 저장: CHOSEN — 실행 중인 세션은 메모리에 유지하고, 검증할 때마다 별도의 검증 이력 파일에 날짜·파일 이름·색상별 건수·오류 메시지·프로그램 버전을 기록한다. 문서 원문·엑셀 전체 데이터·대화 원문은 저장하지 않으며, 이전 세션을 자동 복원하지 않는다.
D08 추가 provider: CHOSEN — Colab의 vLLM을 문맥 연결 비교용 provider로 테스트한다. 기존 Windows 프로그램이 한글·엑셀 파일을 읽고 색상을 적용하며, vLLM에는 민감하지 않은 fixture에서 추출한 문맥과 후보 항목만 전달한다. Ollama는 기본 provider로 유지하고, vLLM은 속도·문맥 연결 정확도 비교에 사용한다.
D09 확장 기능: CHOSEN — 진행 이벤트와 재검증을 첫 버전에 포함한다. “한글 읽는 중”, “엑셀 비교 중”, “색상 적용 중”처럼 현재 단계를 표시하고, 재검증할 때마다 한글 문서를 처음부터 끝까지 다시 읽어 엑셀과 전체 비교한다. 이전 검증에서 프로그램이 직접 표시한 위치만 최신 결과에 맞춰 갱신하고, 사용자가 직접 지정한 색상은 보존한다. 취소·동시 실행·원격 접속은 후속으로 미룬다.

## 최초 범위와 제외 범위
최초 범위: D01~D09 합의 사항. 기존 프로그램 안에서 한글 문서와 엑셀을 읽고, 문맥 기반으로 수치를 비교해 한글 문서에 색상을 적용하며, 진행 이벤트·재검증·검증 이력 기록과 민감하지 않은 fixture 기반 Ollama·vLLM 비교 테스트를 포함한다.
후속 범위: 취소·동시 실행·원격 접속, 그 밖의 합의 기능.
이번 버전에서 제외: PDF·임의 폴더 탐색·임의 셸 실행·자동 저장. D09에서 후속으로 미룬 취소·동시 실행·원격 접속도 제외한다.
기본 제외: 공개 원격 제어 서비스, 임의 시스템 전체 접근, 비밀키 공유. 원격 접속은 별도 설계 없이는 추가하지 않는다.

## 완료 기준
ACCEPTANCE.md의 공통 시나리오에 실제 증거를 남긴다. 실제 모델 한 종류에서 범용 작업과 코딩 작업을 확인하고, 오류·거절도 검증한다. 추가 provider와 저장 재개는 선택한 범위에 따라 확인하거나 제외 사유를 쓴다. 모델 응답의 품질과 프로그램의 도구 실행 성공은 별개로 평가한다.

## 벤치마크 실험
Docker 없이 실행하는 Terminal-Bench Pro 로컬 이식판의 고정 목록으로, 원본 easy 2·medium 4·hard 4를 사용한다. 실행 가능한 Python 예시와 로컬 평가 연결·점수 모니터는 별도 harness-lab 자료로 제공한다. 자신의 구현을 같은 로컬 평가 규격에 연결하거나 예시를 이해하고 개선한다. 높은 점수 자체가 완료 조건은 아니며, 기준 측정과 가설에 따른 변경 후 측정의 실제 결과를 제출한다. 오류·미완료를 분모에서 제외하지 않고 개발용 채점기 진단과 학생 모델 성능을 구별한다.

난이도는 고정된 upstream task.toml의 분류를 유지한다. 경로와 Python 실행을 로컬로 이식한 결과이며 공식 컨테이너 점수가 아니다. 더 다양한 환경을 일관되게 재현할 때 Docker를 사용할 수 있으나 기본 과제에서는 요구하지 않는다.
